# Fraud Detection with Big Data Techniques: Batch (Hadoop/Hive) vs Streaming (Kafka)

Big Data Computing (BDC) mini project. We run the **same synthetic transactions** and the **same detection rules** through two architectures and compare them on detection speed, accuracy, throughput and resource use.

- **Batch:** Hadoop HDFS + Hive (HiveQL window functions)
- **Streaming:** Apache Kafka (KRaft mode) + an in-memory scoring engine in Python
- **Platform:** Google Colab (free tier, about 2 vCPUs and 12 GB RAM), with Google Drive as shared storage between notebooks

Because both pipelines read one shared `config.json`, any difference in results comes from the architecture, not from the rules.

## Architecture

```
Batch:     CSV -> HDFS (hdfs dfs -put) -> Hive external table -> HiveQL rules -> flags CSV + metrics JSON
Streaming: CSV -> Producer (replay at 1K-50K ev/s) -> Kafka topic (3 partitions, key = user_id)
               -> Scoring engine (per-user state) -> fraud-alerts topic + flags CSV + metrics JSON
```

## Detection rules (shared)

| Rule | Definition |
|---|---|
| High amount | amount > user mean + 3 x user std (streaming needs 10 past transactions first) |
| Rapid burst | more than 3 transactions by one user inside 120 seconds |
| Impossible travel | more than 500 km from the user's previous transaction, within 30 minutes of it |
| Odd hour | hour in [0, 5) and amount >= 1500 |

How each pipeline implements them:

| Rule | Batch (HiveQL) | Streaming (Python) |
|---|---|---|
| High amount | `AVG`, `STDDEV_SAMP` per user over full history | Welford running mean and variance over past events only |
| Rapid burst | `LAG(ts, N)` within the user partition | sliding-window `deque` of timestamps |
| Impossible travel | `LAG(lat, lon, ts)` + haversine | last location and time kept per user |
| Odd hour | `hour(event_time)` filter | hour derived from the event timestamp |

## Synthetic data

- Columns: `txn_id, user_id, amount, merchant, merchant_category, city, lat, lon, timestamp, is_fraud, fraud_type`
- Three sizes: 10K, 100K and 1M rows, generated with a fixed seed (reproducible), about 50 transactions per user over 14 days
- 1.5% fraud: high amount 40%, rapid burst 25%, impossible travel 25%, odd hour 10%
- A quarter of each fraud pattern is deliberately subtle (just under the thresholds), so recall cannot be a trivial 100%

## Notebooks

| # | Notebook | What it does | Output (Google Drive `BDC_Fraud/`) |
|---|---|---|---|
| 1 | Data generator | Builds labelled datasets and writes `config.json` | `data/transactions_<size>.csv`, `config.json` |
| 2 | Batch detection | Sets up Hadoop + Hive, loads into HDFS, runs HiveQL rules, evaluates | `results/batch_flags_<size>.csv`, `results/batch_metrics_<size>.json` |
| 3 | Streaming detection | Sets up Kafka, replays events at several rates, scores, evaluates | `results/stream_flags_<size>.csv`, `results/stream_metrics_<size>.json` |

Each of notebooks 2 and 3 ends with its own metrics cell. The side-by-side comparison is in `dashboard/index.html`.

### How to run

1. Upload the notebooks to Google Colab.
2. Run Notebook 1 once. It creates the data and `config.json` on Drive.
3. Run Notebook 2 and Notebook 3 (separate Colab sessions). Re-run their setup cells after any session reset.
4. Open the dashboard and load the metrics JSON files from `BDC_Fraud/results/`.

Notes: Notebook 2 uses Java 8 (Hive 3.1.x does not work on Java 9+) and runs MapReduce in local mode on a pseudo-distributed HDFS. Notebook 3 uses Java 11 and Kafka 3.7.1 in KRaft mode (no ZooKeeper). The 1M-row batch run can take 10 to 25 minutes.

## Metrics collected

| Group | Batch | Streaming |
|---|---|---|
| Speed | end-to-end job time (HDFS load to flags collected), phase breakdown | per-event detection latency: mean, median, p95, p99, max |

| Accuracy | precision, recall, F1, false-positive rate, confusion matrix, recall per fraud type | same, plus recall by position in the stream (cold start) |
| Resources | average and peak CPU, average and peak memory | same |

## Expected trade-offs (what the project tests)

- **Batch** sees the full history, so every transaction has a proper baseline, but flags only exist after the whole job finishes.
- **Streaming** flags each event within milliseconds, but only sees the past, so new users have no baseline (cold start). It also saturates at some event rate, after which consumer lag grows.
- A hybrid (lambda-style) design can combine streaming for fast alerts with batch for full-history re-scoring.
